# deps-conflict-resolver 开发经验总结

本文档总结了 deps-conflict-resolver 在开发过程中遇到的问题和解决方案，供后续维护和类似项目参考。

---

## 依赖分析与冲突检测

### 1. 别名复用只应考虑冲突范围，而非全部范围

**问题**：早期版本在查找可复用的已有别名时，会尝试满足所有 peer 依赖范围（包括已被主工程满足的范围）。例如主工程用 `vue@3.x`，某个库要求 `vue@^2.5.0`，另一个库要求 `vue@^3.0.0`（已被满足）。旧逻辑会把 `['^2.5.0', '^3.0.0']` 全部传入匹配，导致已有的 `aliased-vue2`（版本 2.7.16）无法满足 `^3.0.0`，返回 null，最终重复创建别名。

**方案**：用需要重定向的冲突范围筛选已有别名，并检查候选自身的 peer 依赖。当候选和消费方共享同一个被重定向的 peer 时，候选须兼容消费方实际使用的 provider。

**教训**：复用已有资源时，约束条件应只包含真正需要解决的部分，而不是全部需求。

### 2. pnpm hoisting 导致的误判：resolve ≠ 已声明

**问题**：pnpm 的 peer/hoisting 机制会让某些包在 `node_modules` 中可被 resolve 到，但主工程的 `package.json` 中并未声明。旧逻辑只要能在 node_modules 中找到包就认为"主工程已安装"，导致本应报 missing 的 peer 依赖被错误地触发了别名安装。

**方案**：严格区分"可在 node_modules 中找到"和"在主工程 package.json 中声明"，只有后者才触发自动别名安装逻辑。

**教训**：包管理器的行为差异（npm/yarn/pnpm 的 hoisting 策略不同）会直接影响依赖解析结果，不能简单假设 node_modules 可见 = 已声明。

### 3. Monorepo 场景下"已声明"的定义需要合并 workspace 根

**问题**：在 pnpm workspace 中，依赖可以声明在 workspace 根的 `package.json` 中，子包通过 `workspace:` 协议引用。如果只检查子包自身的 `package.json`，会将根中已声明的依赖误判为 missing。

**方案**：检测到 workspace 环境时，将当前包和 workspace 根的 `package.json` 声明合并判断。

**教训**：monorepo 中依赖声明是分层的，任何关于"是否已安装/声明"的判断都需要考虑 workspace 拓扑。

### 4. 已有别名必须验证身份，安装器不得覆盖目录

**问题**：仅凭 `installSpec` 或目录存在就认为 alias 可复用，会把错误包或错误版本当作目标依赖；直接覆盖已有目录也可能破坏其他使用者。

**方案**：复用前读取 alias 目录的 `package.json`，同时校验真实包名和版本。安装器遇到缺失/无效元数据、包名不匹配或版本不匹配时，返回结构化的 `ALIAS_NAME_OCCUPIED` collision，标记该 alias 失败且不调用包管理器；已有目录保持不变。只有身份和版本都匹配时才复用。

**教训**：安装操作必须是非破坏性的；遇到占用或不确定状态应报告冲突并 fail closed，而不是静默覆盖。生成名称时已预留当前工程与 workspace 根 dependencies/devDependencies/optionalDependencies 的键；安装前后仍需校验实际包身份，不能仅凭名称认为资源属于本库。

### 5. optional peerDependencies 应排除在冲突和 missing 报告之外

**问题**：`peerDependenciesMeta` 中标记为 `optional: true` 的 peer 依赖如果未安装，不应被报告为 missing，也不应触发别名安装。

**方案**：在收集第一层 peer 时检查 `peerDependenciesMeta`，跳过 optional 条目。它们不会进入冲突列表、missing peer 诊断或 alias 生成。

## 性能与稳定性

### 6. 依赖图遍历必须按安装路径保留嵌套实例

**问题**：按包名去重会把同名但不同版本的嵌套包错误合并，导致 importer 解析到错误的 alias；递归调用还可能在深依赖树上耗尽 JavaScript 调用栈。

**方案**：使用显式栈迭代遍历，并以规范化的实际包目录作为图节点身份。每个子依赖都从其所属包目录解析，因此同名嵌套实例保留为独立节点；alias 的 importer 路径按具体实例生成，运行时优先按路径匹配。旧调用方没有 `importerPaths` 时才保留 name-only `allDependents` 兼容路径。

**边界**：冲突检测仍只收集用户指定依赖的第一层 peer；完整递归图只用于重定向候选、路径作用域和 alias-to-alias peer closure，不会把子依赖 peer 自动升级为新的安装任务。`excludeRedirects` 对路径匹配到的实例及其后代生效，`includeRedirects` 仍按显式包名补充后再执行排除。

**教训**：图遍历的去重键必须反映运行时包实例，而不是只反映显示名称；检测范围和重定向范围要分别定义。

### 7. 缓存 null 结果，避免重复磁盘探测

**问题**：`package.json` 查找和模块路径解析涉及大量磁盘 I/O。如果某个路径不存在，每次查询都会重新触发磁盘探测，在大型项目中成为严重性能瓶颈。

**方案**：LRU 缓存同时缓存成功结果和 null 结果，设置合理的缓存上限（package.json 缓存 5000、路径缓存 20000）。

**教训**：缓存不仅应缓存命中结果，也应缓存未命中结果（negative cache），尤其在 I/O 密集场景。

### 8. 同步 I/O 在分析阶段优于异步 I/O

**问题**：分析阶段需要大量细粒度的文件读取（数百个 package.json），如果全部用异步 I/O，微任务调度的开销反而超过了 I/O 本身的收益。

**方案**：分析阶段使用同步 `readFileSync`，安装阶段使用异步 `spawn`（外部进程，天然异步）。

**教训**：异步不一定比同步快。大量小规模 I/O 操作中，同步方式因省去事件循环调度开销可能更优。应根据场景实测，而非教条地"一切异步"。

## 包管理器兼容性

### 9. npm 安装和冻结重装需要使用一致的 peer 选项

**问题**：宿主与旧包的 peer 范围可能互斥，普通 npm 安装会因冲突报错。用 `--legacy-peer-deps` 生成锁文件后，冻结重装也需要沿用该选项。

**方案**：别名安装时传递 `--legacy-peer-deps`。在 npm 项目中运行 `prepare` 后，CI 使用 `npm ci --legacy-peer-deps`，再以 `offline: true` 和 `strict: true` 构建。

### 10. 安装进程需要有边界的超时和信号升级机制

**问题**：网络问题或 registry 不可达时，`npm install` 可能无限挂起。

**方案**：

- 包管理器安装子进程设置 120 秒超时
- 超时后先向进程组发送 SIGTERM，等待 5 秒
- 若进程组仍未退出，再发送 SIGKILL（Windows 使用 `taskkill /pid <pid> /t /f`）
- 以子进程 `close` 事件作为最终完成信号，`settled`/`closeSeen` 只负责保证 Promise 单次完成

这个计时器约束的是 alias 安装子进程，不应被表述为覆盖 registry 响应体读取或 `response.json()`；registry-client 已为 fetch 与响应体读取共用一个 AbortController 和时间预算；两套超时机制相互独立。

**教训**：外部进程必须有超时和优雅降级；超时结果应在子进程真正退出后报告，不能用 `child.killed` 或提前 resolve 代替完成信号。

### 11. 包管理器自动检测需要多重降级策略

**问题**：不同项目使用不同的包管理器，硬编码会导致兼容性问题。

**方案**：三级降级检测：

1. `package.json` 的 `packageManager` 字段
2. lock 文件存在性（`pnpm-lock.yaml` / `yarn.lock` / `package-lock.json`）
3. 默认 npm

在 workspace 根目录安装别名时，pnpm 使用 `-w`，Yarn Classic 使用 `-W`。用包管理器声明或实际运行版本区分 Yarn Classic 和现代 Yarn。

显式 `registry` 同时用于版本查询和别名安装。省略时，安装继承包管理器自身的配置，版本查询依次检查环境变量、项目级配置（Yarn 优先读取 `.yarnrc.yml`）、用户级配置，再回退到 npm 公共源。

## 构建工具插件

### 12. Webpack 插件应在 normalModuleFactory 阶段拦截

**问题**：Webpack 有多个阶段可以拦截模块解析（resolve hook、normalModuleFactory、compilation）。选择不当的阶段会导致拦截时机过晚或需要复杂的 resolve 链处理。

**方案**：在 `normalModuleFactory.hooks.beforeResolve` 修改 `resolveData.request`，把后续入口和条件导出的解析交给 Webpack。

**额外处理**：

- `watchRun` 验证已发布的依赖快照，输入变化时重新分析
- 宽松模式下，初始化抛错后停用当轮重定向并继续编译。异常和错误诊断都会保留恢复所需的文件监听
- Webpack `done` hook 中的错误不应抛出
- Webpack 开启 `strict` 时将初始化错误交给编译器。核心 resolver 与 Vite 插件将初始化错误交给调用方

### 13. Vite 插件需要处理 esbuild 版本差异

**问题**：esbuild 0.17+ 提供了 `build.resolve` API，但更早版本没有。直接调用会在旧版 esbuild 上崩溃。

**方案**：运行时检测 `typeof build.resolve === 'function'`，旧版降级为从工程根目录进行 Node 解析；Vite 8 使用原生 Rolldown resolveId 适配，而非依赖 esbuild 插件的兼容转换。

### 14. Vite 插件在 dev/build 模式下应可独立开关

**问题**：某些场景只需要在生产构建时启用别名（dev 模式下冲突库不参与开发），但插件默认在所有模式下都生效。

**方案**：提供 `enableInDev` 和 `enableInBuild` 选项，禁用时返回 `undefined` 配置让 Vite 跳过。

## 模块解析与路径处理

### 15. 必须排除冲突目标包本身，避免主工程引用被重定向

**问题**：分析结果中的"相关包列表"会包含 peer 依赖声明中的目标包名（如 `vue`）。如果不排除，主工程代码中 `import Vue from 'vue'` 也会被重定向到别名版本。

**方案**：在收集完所有相关包后，显式移除冲突目标包名。

### 16. Windows 绝对路径需要特殊处理

**问题**：Windows 路径如 `C:\project\node_modules\foo` 会被错误地解析为包名 `C`。

**方案**：在提取 importer 包名时，用 `/^[a-zA-Z]:[\\/]/` 检测 Windows 绝对路径并跳过。

### 17. pnpm 的 `.pnpm` 目录必须跳过

**问题**：pnpm 的 node_modules 结构包含 `.pnpm` 虚拟存储目录，路径中包含大量中间目录。如果不过滤，会从路径中提取出 `.pnpm` 等无效包名。

**方案**：遍历 node_modules 路径时，跳过以 `.` 开头的目录段。

### 18. scoped 包的正则转义

**问题**：`@scope/pkg` 生成的正则表达式中，`/` 需要转义，否则会匹配到 `@scopeXpkg` 等错误路径。

**方案**：使用 `escapeRegex` 工具函数处理所有动态生成的正则片段。

### 19. 相对路径、绝对路径、虚拟模块不应被重定向

**问题**：构建工具的 resolve hook 会收到各种非包名请求（`./utils`、`/abs/path`、`webpack/runtime`、`virtual:module`），这些不应该进入别名解析。

**方案**：在插件层使用 `isPathLikeRequest` 和 `isWebpackInternalRequest` 过滤，只处理裸模块名（bare module specifiers）。

## 工程实践

### 20. Logger 使用全局级别避免子模块日志丢失

**问题**：入口开启 debug 模式后，子模块各自创建的 logger 实例仍然使用默认 INFO 级别，导致关键调试信息不输出。

**方案**：子模块共享默认日志级别。`debug: true` 启用全部日志，并保留 warn/error。CLI 通过 `AsyncLocalStorage` 只静音本次准备调用的日志，保留 JSON 输出完整性和同进程其他调用的日志。

### 21. semver 操作必须 try/catch

**问题**：用户项目中可能包含非标准的版本号（如 git URL、file: 协议、自定义 tag），直接传入 `semver.satisfies` 会抛异常。

**方案**：所有 semver 包装函数都用 try/catch 包裹，返回安全的默认值（`false` / `0`）。非标准版本号在生成别名名时取首段数字，兜底为 0。

### 22. 别名命名需要冲突解决策略

**问题**：同一包的不同版本可能生成相同的别名（如 `vue@2.6.14` 和 `vue@2.7.0` 都生成 `aliased-vue2`），导致安装冲突。

**方案**：对已识别的 alias 名称使用三级候选策略：

1. 简单名：`aliased-vue2`
2. 完整版本后缀：`aliased-vue-2-6-14`
3. 数字计数器：`aliased-vue2-2`

安装器仍会在落盘前验证实际包名/版本；即使目录已被其他包占用，也只报告 `ALIAS_NAME_OCCUPIED` 并保留原目录。名称候选集合已包含当前工程和 workspace 根 dependencies/devDependencies/optionalDependencies 的键。实际目录占用仍由安装前后校验处理；退出码成功而无法找到有效 alias 时也应报告失败。

### 23. 双重初始化应为 no-op

**问题**：在复杂构建配置中（如 Webpack 多配置 + watch 模式），`initialize()` 可能被多次调用。

**方案**：`initialize()` 内部检查状态，已初始化则直接返回。同时用 promise 缓存初始化过程，避免并发初始化。

## 解析与准备的性能复盘

### 24. 目录缓存在密集、稀疏和分散导入中表现不同

旧实现按 importer 和目标包缓存解析决策。同一次构建遍历超过缓存容量时，文件路径也会被反复淘汰，导致对同一批文件重复调用 `realpathSync`。第一版优化在同一目录出现第二个不同 importer 时就枚举整个目录。它显著加快了同目录的批量导入，但引出了两个不同的开销。

- 在大目录只导入两个文件时，`readdirSync` 已经分配了全部目录项，之后才检查容量。
- 在大量小目录请求两个目标包时，走目录快路径的文件缺少可回退的文件路径缓存。目录项和文件决策一起被淘汰，热遍历再次访问磁盘。

最终版在同一目录被四个不同 importer 请求后才尝试共享决策。每个新请求的文件先用 `lstatSync` 确认类型，只缓存已访问的普通文件。不符合条件的文件走原有逐文件解析。目录物理路径可以复用，目录、已验证文件和决策有各自的容量上限。这样在目录预热后，尚未解析的普通文件若被替换为 symlink，首次解析仍会跟随链接。

通用路径解析恢复使用 `realpathSync`。多级 symlink 的目标包含 `..` 时，`.native` 和 JS 实现可能解析到不同目录。带 `?` 或 `#` 的 importer 先尝试完整字面路径，之后才探测后缀。确认后复用同一源文件的物理路径，并为这一缓存保留独立容量，避免 Vue 子请求挤掉模块 ID 路径。

以下为 macOS arm64、Node 22.14.0 上三轮合成基准的中位数。冷解析遍历一次，热解析随后遍历两次。基线为 `149fa71`，全目录扫描版是复盘时的中间工作区版本。

| 场景                                        | 基线（ms） | 全目录扫描版（ms） | 最终版（ms） |
| ------------------------------------------- | ---------: | -----------------: | -----------: |
| 同目录 20,000 个文件，一个目标包，冷解析    |     551.45 |              23.26 |        85.98 |
| 同目录 20,000 个文件，一个目标包，热解析    |   1,172.86 |              25.70 |        41.28 |
| 20,000 项目录中只导入 2 个文件，冷解析      |       0.11 |              10.66 |         0.11 |
| 2,000 个目录各 2 个文件，两个目标包，热解析 |      78.82 |             247.65 |        74.86 |
| 1,500 个目录各 4 个文件，两个目标包，热解析 |     469.28 |             231.88 |        98.82 |

最终版的密集冷路径执行 3 次 `realpath` 和 19,997 次 `lstat`，逐文件校验的代价体现在冷耗时上。表中的各组热解析均无 `realpath`、`lstat` 或目录枚举调用。用 `pnpm bench:scale` 复测，也可给 `node benchmarks/scale.cjs` 传入其他 checkout 的路径，用同一套负载对比。[基准脚本](../benchmarks/scale.cjs)

后续把 `ImporterInfo` 合并进模块路径缓存的试验，让分散和组件布局的热解析分别缩短约 9% 和 8%。相同布局填充缓存并强制 GC 后，净保留堆增加约 1.3–1.5 MiB。当前分别限制路径和 importer 信息的容量，保留这部分常驻内存余量。

### 25. 可能安装依赖的准备需要连续持有独占锁

两阶段准备让解析器先持共享读锁，发现缺少 alias 后重新进入队列申请写锁。两次排队之间存在空窗。已完成读取的实例可能提前报告初始化完成，随后在另一实例安装时抛 `PROJECT_STATE_CHANGED`。同一进程内，后到的离线 strict 初始化也可能先于写阶段执行。跨进程时，它可以在在线解析器持读锁等待 registry 的期间读到尚未安装的状态，报 `OFFLINE_ALIAS_MISSING`。

任何可能调用包管理器的正式准备都从分析开始持有独占锁，直到发布结果。只读初始化可跨进程共享读锁，用户回调仍在锁外执行。同时为每次准备创建独立的 registry 客户端，使修正安装可以复用已取到的元数据。曾用同进程两个工程复现过干扰，另一个工程结束后清空共享缓存，原工程的修正安装被第二次请求的暂时失败打断。[准备回归测试](../tests/core/preparation.test.ts) · [跨进程锁测试](../tests/core/project-preparation.test.ts)

### 26. Vite 兼容矩阵需要覆盖默认请求过滤

原来的 Vite 4–8 兼容脚本始终使用 `strict: true`。这种模式下每个裸模块请求仍可触发快照检查，Vite 环境和 Rolldown 的新请求过滤因此关闭。单测能检查正则和返回的 hook 形状，真实打包器运行才覆盖原生过滤、预构建、SSR 和 Worker 的组合。

现有 `vite-compat` 作业在同一份构建产物和 Vite 安装上额外运行 `--non-strict`。strict 用例继续覆盖诊断路径，默认用例覆盖过滤路径。Vite 8.3.8 上含 1,500 个无关请求的合成构建中，插件回调从 1,503 次减到 1 次，总构建约为 41–43 ms。CI 验证解析行为和运行时实例一致性，耗时数据留在基准对照中。[CI 配置](../.github/workflows/ci.yml) · [兼容脚本](../tests/compat/vite.mjs)

Vite 在准备完成后确定 `beforeResolve`。关闭 strict 且只有观测回调时，环境和预构建继续按生效 alias 的原包名过滤。配置自定义解析时，esbuild 和 Rolldown 都将依赖内部的模块请求交给该回调。预构建缓存身份包含规则指纹、预构建策略版本和回调的缓存键。[构建回归测试](../tests/plugins/vite/lifecycle.test.ts) · [预构建兼容测试](../tests/compat/vite.mjs)

早期工作区曾用 `hooks` 对象是否存在来决定过滤，纯观测的 `onAnalysisComplete` 也会关闭过滤。同一个 Vite 7.3.2 依赖打包样本中，修正后真正进入 `resolveId.handler` 的次数从 45,783 降到 53，重定向均为 51 次，输出大小和 Vue 运行时版本一致。计数时需要保留原生 `filter`，只包装 handler。准备完成后再确定回调，能保留观测钩子的过滤，也支持在准备回调中注册 `beforeResolve`。观测回调前的分析候选只在 revision、配置及已观测输入一致时复用。

两个源码相同的 `beforeResolve` 闭包可以返回不同目标。Vite 的显式 `beforeResolveCacheKey` 标识回调读取的外部状态，回调源码也参与失效。自定义回调缺少键时，配置解析会触发重新预构建。预构建策略变更影响产物时，需要更新缓存版本，让升级后重新生成产物。Vite 的 `logLevel` 和 logger 在准备阶段确定，运行期歧义只在登记新诊断时调用绑定的告警回调，保留结构化诊断和严格模式报错。

### 27. Watch 输入快照需要和分析结果一起发布

原版在 `apply` 启动分析，首轮 `watchRun` 又失效并分析一次，后续每轮也重新分析。把准备放到实际编译生命周期可以去掉首轮双跑。后续复用还需要确认分析用到的输入。

最初把快照整理放在 Webpack 层。首次 `watchRun` 释放准备锁后，排队的安装可以改变依赖图，观察者随即替换分析结果。这时插件仍可能把旧输入和新规则拼到一起。后来恢复旧清单，再改一个源码文件，校验会通过并继续使用错误规则。

现在由 Resolver 在准备锁内绑定分析结果、输入和 revision，并同时观察锁文件。观察者替换结果时取消旧快照。复用前后都检查它是否仍然对应已发布结果。刷新会等待在途准备，回调重入同一刷新会提前报错。在线初始化期间若并发写入引入新的待安装 alias，初始化最多补做一次持锁准备。

源码修改、删除及空 `invalidate()` 都可以走输入校验。分析没变时仍清理 importer 缓存，因为源码下的软链和未纳入依赖图的局部清单可以单独变化。监听订阅在异常或错误诊断后保留，暂时消失的清单归入 `missingDependencies`，文件恢复即可唤醒下一次编译。已验证 alias 的物理目标变化时，Webpack 更新对应的解析缓存身份并清理文件系统读取缓存，无关模块可以继续复用。 [Webpack watch 回归](../tests/integration/webpack-watch.test.ts) · [并发准备回归](../tests/core/preparation.test.ts)

### 28. 包清单查找需要区分缺失和不可读

子应用残留的空目录、坏掉的包目录软链和不可穿越的祖先都曾让查找过早停在近处，漏掉上层已安装的包。现在按 Node 提供的查找顺序核验 `package.json`，从当前文件系统获取物理身份。若确实能看到最近的清单但无法读取，则保留诊断。实测该清单自身的循环软链可以让 `require.resolve('pkg/package.json')` 回退到上层，同时裸包仍加载最近目录的 `index.js`，因此两种请求需要分别验证。

依赖准备期间，同一个缺失的查找目录可覆盖其下多条未命中请求。目录本身成为校验输入，随后出现时会触发重新分析。在已启用 watch 复用的两版对照中，同一次源码更新的同步文件探测由 20,225 次降到 13,344 次，`readFileSync` 调用均为 939 次。探针减少的比例与实际耗时下降分开观察，`stat`、路径解析和文本哈希的单次成本不同。校验继续使用清单内容哈希。用 `existsSync` 单独重放时，路径缺失和后来出现的循环链接都会得到 `false`。 [物理路径回归](../tests/utils/package-path.test.ts)

### 29. 固定依赖图后再对照宿主性能

以下对照以 1.6.0 发布提交 `f801b8d` 为基线，在 macOS arm64、Node 22.14.0 上使用相同安装树和插件选项，交替运行七轮并取中位数。Vite 和 Webpack 样本的分析结果分别包含 672 和 715 个包名。每个样本在修改前后的解析指纹和抽查请求结果一致，均无 registry 请求。早期接入版本在 pnpm 树中存在漏扫和产物差异，适合用来复现正确性问题。表中的时间比较使用同等解析结果的版本。

| 场景                                  | 1.6.0（ms） | 修订后（ms） | 全图分析次数 |
| ------------------------------------- | ----------: | -----------: | -----------: |
| Vite 宿主，核心初始化                 |       212.6 |        220.8 |        1 → 1 |
| Vite 宿主，初始化带观测回调           |       392.8 |        318.2 |        2 → 1 |
| Webpack 宿主，核心初始化              |       242.6 |        251.3 |        1 → 1 |
| Webpack 5.100.2，首次 watch 准备      |       549.5 |        346.0 |        2 → 1 |
| Webpack 5.100.2，源码保存后的准备     |       214.6 |         74.7 |        1 → 0 |
| Webpack 5.100.2，删除无关源码后的准备 |       210.2 |         71.9 |        1 → 0 |

Webpack 的计时截至 `watchRun` 结束。单次核心分析的耗时略增，收益集中在省下的重复分析。用 Vite 7.3.2 复核同一实际入口的一对生产构建，耗时约 15 秒，前后均有 10 个 chunk，输出文件合计 9,169,413 字节，产物 SHA-256 一致。复测时固定入口、安装树和选项，同时核对重定向、运行时版本及产物，再解释耗时差异。

## 总结

| 类别         | 核心教训                                                          |
| ------------ | ----------------------------------------------------------------- |
| 依赖分析     | 约束条件只取需要解决的部分；resolve ≠ 声明；monorepo 声明需合并根 |
| 性能         | 迭代替代递归；负缓存同样重要；大量小 I/O 用同步可能更快           |
| 包管理器兼容 | 永远不要假设单一包管理器行为；安装进程必须有超时                  |
| 构建工具插件 | 选择最早的拦截时机；处理版本差异；初始化失败不能阻塞构建          |
| 路径处理     | 区分裸模块名和路径；处理 Windows 路径；跳过虚拟存储目录           |
| 工程实践     | 外部输入全部容错；命名需要防冲突策略；重复调用必须幂等            |
